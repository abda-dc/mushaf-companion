# M12.2 — Adhan & Notifications

## Scope

M12.2 adds opt-in five-Salah notifications to the existing M12.1 Prayer & Qibla feature. It does not add another prayer calculation library, a remote prayer API, Web Push infrastructure, or Islamic Foundations content. Sunrise remains contextual solar information and is never an Adhan target.

## Architecture

The notification path is:

`app/prayer-times.ts` (`adhan@4.4.4`, device-local) → `app/prayer-notification-scheduler.ts` (pure plan/reconciliation) → `app/prayer-notification-platform.ts` → native or web adapter.

`app/prayer-notification-controller.ts` calculates a seven-calendar-day horizon through the existing prayer calculation function. The React panel does not construct Capacitor payloads or duplicate Salah calculation logic. `PrayerNotificationLifecycle` performs bounded startup/foreground reconciliation and registers notification-tap navigation; it never requests permission.

## Permission behavior

Notifications default to off. Loading the app, opening Prayer, migrating preferences, registering the service worker, startup reconciliation, and foreground reconciliation only inspect existing permission. The OS/browser prompt is called only from the user-controlled enable or test actions. A denied state does not affect prayer calculations, Qibla, location preferences, or Quran reading.

## Native scheduling and reconciliation

The installed Android/iOS app schedules up to seven days (35 alerts) using absolute `Date` values produced by the existing calculation layer. Past entries and disabled Salah toggles are excluded. IDs are positive deterministic integers derived from local calendar day plus Salah index in a reserved range. Payload metadata contains only the owner namespace, Salah, local date, alert mode, optional approved cue ID, and the Prayer navigation target.

Before adding alerts, the adapter reads pending notifications and selects only entries with both the M12.2 owner marker and reserved prayer ID. Matching entries remain. Stale or duplicate owned entries are cancelled by ID, then missing entries are added. Unrelated notifications are never passed to `cancel`, and ordinary reconciliation never calls `cancelAll()`.

Changes to calculation method, Asr method, adjustments, location, individual Salah choices, alert mode/cue, master state, or a detected foreground/time-zone transition invoke the same idempotent reconciliation. With a temporary, non-remembered location, the current panel can calculate the horizon without persisting coordinates. Later extension requires a current or opted-in remembered approximate location; previously calculated OS alerts remain unless notifications are disabled.

## Android

The official `@capacitor/local-notifications@8.3.1` plugin handles Android 13+ display permission. `SCHEDULE_EXACT_ALARM` is declared; `USE_EXACT_ALARM` is deliberately absent. The UI checks `checkExactNotificationSetting()` and offers a user-triggered `changeExactNotificationSetting()` action when exact alarms are unavailable.

Exact access is never opened implicitly. With access, prayer alerts use exact scheduling and `allowWhileIdle` for the user-requested Salah alert only. Without access, payloads explicitly set inexact scheduling and the UI reports degraded timing. The stable `prayer-default-v1` channel uses the system notification sound. Future approved cues receive bounded `prayer-adhan-<asset>-v1` channels rather than mutating an existing channel.

## iOS

The Local Notifications plugin schedules device-local alerts that follow normal iOS foreground, background, and closed-app behavior. Foreground presentation is configured for banner/list/sound. Focus, Silent Mode, permission, and other OS policy remain under user control.

Apple notification sounds must be under 30 seconds. Only an approved registry record with purpose `notification-cue`, compatible native placement, duration under 30 seconds, provenance, license, revision, and checksum may be selected. A full Adhan recording is a separate foreground/user-initiated concept and is not promised from a closed-app notification.

## PWA

The web adapter feature-detects `Notification`, a secure context, and service-worker availability. It supports explicit permission and a user-triggered test notification. The canonical workers `public/sw.js` (main app) and `pages-static/sw.js` (GitHub Pages template) preserve their existing install/activate/fetch caches and add notification-click focus/open navigation to `#prayer`. `scripts/build-pages.mjs` generates the Pages build worker from `pages-static/sw.js`; generated output must not be edited independently.

No browser timer, experimental Notification Triggers API, or periodic background execution is used. Reliable timed delivery after an installed PWA/browser is closed requires a future Web Push subscription and remote sender. M12.2 defines that boundary but does not transmit or store coordinates for push.

## Privacy and offline behavior

Prayer calculations and native scheduling remain device-local and work without a prayer service after the horizon is scheduled. Coordinates are neither transmitted nor embedded in notification payloads. Exact coordinates are not persisted by notification enablement. The existing opt-in remembered location remains rounded to three decimal places.

## Preference migration

`mushaf:prayer-v2` is the current schema. When no valid v2 value exists, the loader reads `mushaf:prayer-v1`, preserves method, Asr choice, all adjustments, remember-location state, and rounded remembered coordinates, adds safe notification defaults, and writes a v2 copy. The v1 record is not destructively removed. Malformed notification values and unapproved cue IDs fall back to notifications off/system sound.

## Adhan asset licensing

`app/adhan-assets.ts` is the distribution registry. It is intentionally empty because repository inspection found no approved redistributable Adhan cue. **External resource required: approved redistributable Adhan notification audio.** Until an asset passes licensing/provenance and platform-duration review, the system notification sound keeps the feature operational. No recorded audio is distributed by M12.2.

## Automated testing

Focused tests cover v1 migration, malformed preferences, the Sunrise invariant, future-only multi-day planning, stable IDs/collisions, idempotent/stale/duplicate reconciliation, platform capability states, denied permission, exact-alarm fallback, payload privacy, web permission/test behavior, service-worker navigation, and the absence of fake browser background scheduling. The full repository validation remains `npm test`, `npm run lint`, `npm run build:pages`, `npm run verify:pages`, and `npm run mobile:sync`.

## Manual QA checklist

### Web desktop

- Open Prayer and confirm no permission prompt appears.
- Enable browser notifications and confirm the prompt follows that click only.
- Send a test notification; tap it and confirm Prayer opens.
- Deny permission and confirm the non-blocking blocked state.
- Confirm prayer calculations and existing PWA caching are unaffected.

### Installed PWA

- Validate explicit permission and test display on the target platform.
- Tap the test and confirm the existing window focuses or a new Prayer URL opens.
- Confirm the UI does not promise closed-app scheduling without Web Push.

### Android native

- Validate permission grant/denial on Android 13+.
- Schedule Fajr only, then all five Salah; verify no Sunrise alert.
- Validate test alert and default sound/channel.
- Test exact-alarm allowed and disallowed/inexact states.
- Background and close the app; validate scheduled delivery and notification tap.
- Change method, Asr, adjustment, location, and Salah toggles; inspect idempotent replacement.
- Disable notifications and confirm owned pending alerts are removed while unrelated alerts remain.
- Confirm schedule survives ordinary restart/foreground lifecycle.

### iOS native

- Validate explicit permission, test display, and default system sound.
- Test foreground, background, and closed-app scheduled delivery.
- Validate selected Salah toggles and notification-tap navigation.
- Confirm Focus and Silent Mode remain under user/OS control.
- After an approved cue exists, verify native bundling, attribution, format, and duration under 30 seconds.
